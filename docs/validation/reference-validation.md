# Reference Validation

OpenMeasure's `core/` modules are tested against hand-calculable and
internally-fixed values (see each module's `tests/`). This document is a
second, independent layer: it checks OpenMeasure's calculations against
established external implementations, not against expected values that
were themselves calculated using OpenMeasure.

This is cross-implementation validation, not a restatement of the unit
tests. A discrepancy here means OpenMeasure and an independent, widely
used implementation disagree on the same data under matching definitions,
which is a stronger signal than an internal test passing.

## Method

For each statistic:

1. State the exact definition and defaults OpenMeasure uses (see the
   module's `core/` docstrings).
2. Pick a small, fixed dataset small enough to hand-inspect.
3. Compute the statistic three ways where practical:
   - **Hand**: the textbook formula applied directly (a standalone script,
     no call into OpenMeasure's code, no external package).
   - **OpenMeasure**: the actual shipped `core/` function.
   - **Reference software**: an established, independently maintained
     implementation, matched on definition (not just by name - see
     "Definition notes" below for cases where a package's default differs
     from OpenMeasure's and had to be adjusted to compare fairly).
4. Record the results in the table below with a tolerance and verdict.
5. Any discrepancy is investigated before anything is changed.
   OpenMeasure is not edited to force agreement; either the difference is
   explained by a documented definitional choice, or a real bug is found
   and fixed on its own merits.
6. Confirmed comparisons are converted into automated regression tests
   that hardcode the externally-validated expected value (not a value
   generated by OpenMeasure itself), so future changes cannot silently
   drift away from the reference without a test failing. These tests do
   not call the reference software at test time (see "Tooling" below).

## Tooling

Reference software used for generation is a **dev-only, one-time
comparison tool**, not an OpenMeasure runtime dependency. It is not
listed in `requirements.txt` and is not invoked by the automated test
suite. The generation scripts live in `scripts/validation/` for
transparency and re-runnability, but are run manually, not in CI.

- `scripts/validation/reliability_reference.py` - hand-formula and
  OpenMeasure legs (numpy/pandas only, already OpenMeasure dependencies).
- `scripts/validation/reliability_reference.R` - the R `psych::alpha()`
  leg. Requires R and the CRAN `psych` package, neither of which this
  repository installs or depends on.

**Session note (2026-08-27):** generating a secondary Python reference
(`pingouin`) via `pip install pingouin` was run without a project-local
virtual environment and modified the base Anaconda environment shared by
other projects on this machine (upgraded `pandas`, `statsmodels`,
`scikit-learn`; installed `pingouin`). All upgraded versions still satisfy
this repo's `requirements.txt` constraints and the full reliability test
suite passed afterward, so it was not unwound. Going forward, any
reference-software installs for this kind of one-time comparison should
happen in a throwaway/isolated environment, not the environment this
project's own app runs in.

### Definition notes

- **Cronbach's alpha**: OpenMeasure computes raw (covariance-based) alpha,
  `alpha = k/(k-1) * (1 - sum(item variances) / variance(total score))`,
  using sample variance (`ddof=1`). This is the same "raw_alpha" that R's
  `psych::alpha()` reports and the same value `pingouin.cronbach_alpha()`
  returns, so no adjustment was needed to compare them.
- **Corrected item-total correlation**: OpenMeasure correlates each item
  with the sum of all *other* items (the item excluded from its own
  total). This matches `psych::alpha()`'s `r.drop` column, not its
  uncorrected `raw.r` column (which includes the item in the total) - the
  comparison below uses `r.drop`.
- **Alpha if item dropped**: OpenMeasure recomputes raw alpha on the
  remaining items. This matches the `raw_alpha` column of
  `psych::alpha()`'s `alpha.drop` table (there is also a standardized
  variant in that table, `std.alpha`, which was not used).
- **Split-half reliability**: OpenMeasure splits by fixed item
  *position* (1st, 3rd, 5th, ... vs 2nd, 4th, 6th, ...), not a random or
  content-matched split. `psych::alpha()`'s built-in `splitHalf()` uses
  random splits by default and is not comparable as-is. The R script
  therefore does not call `splitHalf()`; it reproduces OpenMeasure's exact
  odd/even positional split independently in R (`rowSums` over the same
  column indices, then `cor()`), so both sides are computing the same
  defined quantity.
- **Spearman-Brown correction**: `(2r) / (1 + r)` applied to the same
  split-half correlation above, independently applied on the R side
  rather than taken from a package default.

No discrepancies were found. All Reliability statistics in
`core/reliability.py` agree with an independent hand derivation and with
R's `psych::alpha()` (the standard reference implementation for this
statistic) to full floating-point precision on both datasets.

Interrater agreement statistics (`core/interrater.py`: Cohen's kappa,
Fleiss' kappa, Krippendorff's alpha) are out of scope for this pass: they
already wrap `statsmodels` and the `krippendorff` package directly rather
than reimplementing the statistic, so there is no separate OpenMeasure
implementation to validate against those same libraries.

## Adding another module

To extend this document to a new module (Impact Evaluation, Fairness,
etc.):

1. Add a new `## <Module>` section following the same shape: datasets,
   definition notes (especially any place a common package's default
   differs from OpenMeasure's and needs adjusting to compare fairly),
   and a results table with the same columns.
2. Add a `scripts/validation/<module>_reference.py` (and `.R` if a CRAN
   package is the best-matched reference for that statistic).
3. Record every applicable statistic, including any marked
   **Unavailable** (no suitable independent reference exists) rather than
   omitting them silently.
4. Convert confirmed comparisons into regression tests in that module's
   `tests/`, citing this document.
